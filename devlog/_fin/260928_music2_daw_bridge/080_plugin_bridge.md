# 080 — Optional external plugin bridge (wp9)

**Summary.** [I] A Song v1 track may opt into up to four external **effect** plugins by ID. `music2 render --allow-plugins` resolves those IDs from user-owned configuration, passes stereo float32 WAV and one JSON request to an isolated subprocess, and injects its stereo result after track inserts and before gain/pan/duck. A song never supplies an executable, arguments, plug-in binary path or preset path. Missing or disabled capability exits 3. Plugin-processed audio is explicitly outside the byte-determinism claim; songs without plugins retain the old path. D9/D14 are binding (`evidence/main-decisions.md:13,18`); F24 supplies the track placement and injection seam (`evidence/architect-proposal.md:615-628`); R4 §5–§6/§7.E supplies the researched host boundary.

**Depends on:** wp2 optional-field/absent-in/absent-out and legacy baseline; wp8 precedes wp9 only in the serialized execution order of `000_plan.md` (the effect bridge itself needs no MIDI projection); current `src/song/song.schema.ts:21-43,78-89,123-127,292-369`, `src/render/render.schema.ts:4-6`, `src/render/mixer.tool.ts:279-336`, `src/cli/commands/render.ts:53-89`, and `src/shared/paths.tool.ts:6-8`. If wp5/6 have landed, retain their audio-track and automation branches without changing their signal order.

**Consumed by:** wp10 user CLI/skill documentation and examples; `doctor` capability reporting; `export stems`, `export als --content audio|both` and `export dawproject --content audio|both` pass the same opt-in processor into rendering. `export midi`, `export ir`, and DAW exports with `--content midi` never need a host; editable MIDI/device graphs cannot reproduce the external effect and warn about that loss.

## Scope

**IN:** optional `track.plugins` effect chain; user config and explicit command override; `RenderOptions.external` injection; `render` and audio-producing `export stems|als|dawproject` accept `--allow-plugins [--plugin-host <JSON-argv>]`; `doctor --plugins`; bounded JSON+float WAV contract; stub-host tests and optional MIT Python bridge file; source-function and licensing docs. **OUT:** `instrument:"plugin:<id>"`, MIDI-instrument hosting, live/interactive plugin UI, arbitrary command or plugin path in a song, auto-installation, bundling pedalboard/wheels, plugin state blobs/presets, sidechain routing, plugin parameter automation, native DAW plugin serialization, and promising third-party plugin determinism. This chooses F24's track-level form over a new instrument prefix (I). `track.plugins` applies to instrument tracks in wp9; extending it to `audioTracks` requires a later explicit contract.

`V` means a source fact verified in this checkout or by R4's cited documentation; `I` means a music2 implementation choice. No external plugin was executed for this plan.

## 1. Song shape and placement

[I] Choose F24's `track.plugins`, not a `plugin:` instrument. The song can name only a stable logical ID and values; a plugin file path is allowed **only in user config**, as D9/D14 permit. IDs match existing track IDs (`src/song/song.schema.ts:55`). Every plugin is an effect on a rendered instrument track; the host sees the track's stereo buffer after music2 inserts, before track gain, pan, ducking, sends and stem capture. Four stages maximum; duplicates are rejected rather than silently run twice. No effects in a song means no new resolved property and no new render branch.

```ts
export type PluginValue = number | string | boolean;
export interface PluginUse { id: string; params?: Readonly<Record<string, PluginValue>> }
export interface Track { plugins?: PluginUse[] /* 0..4; existing fields unchanged */ }
export interface ResolvedTrack { plugins?: PluginUse[] /* omitted when input absent */ }
```

[I] `plugins` is an array of 0..4 objects with `additionalProperties:false`, required `id`, optional `params`. `id` is `^[a-z][a-z0-9_-]{0,31}$`; ≤32 param names per stage match `^[A-Za-z][A-Za-z0-9_]{0,63}$`; numbers are finite, strings ≤256 UTF-8 bytes with no NUL, booleans accepted. Reject `command`, `argv`, `path`, `pluginName`, `presetFile`, `presetDataB64`, URLs and any unrecognized key at `$.tracks[i].plugins[j].<key>` with `E_SCHEMA` exit 2. The JSON schema describes the value union; code-level validation enforces finite numbers, byte lengths and duplicate IDs. Resolved arrays preserve declared order and keys in lexically sorted order for stable request JSON. `track.plugins:[]` stays explicit but does not activate capability. A `kind:"drums"` or `"notes"` instrument track may use effects; neither is interpreted as a plugin instrument. ProjectIR carries IDs/params solely for an audit and warnings; never a host command or a plugin path.

## 2. Config, command authority and detection

[I] The user-owned file is `${music2Home()}/plugins.json` (V: home resolution at `src/shared/paths.tool.ts:6-8`), with an exact v1 schema:

```json
{"version":1,"plugins":{"softclip":{"path":"/user/installed/SoftClip.vst3","pluginName":null,"command":["/user/venv/bin/python","/user/music2-plugin-bridge.py"],"timeoutMs":60000}}}
```

The example paths describe the **config format**, not committed paths or shipped files. One ID maps to one plugin binary/bundle, one command argv, optional `pluginName` (default `null`), `timeoutMs` default 60000 and range 1000..120000. Config may omit `command` when a global `--plugin-host` or `MUSIC2_PLUGIN_HOST` supplies it. For the process used to run all configured IDs, precedence is CLI flag > environment > per-ID config. CLI/env values are a JSON array of 1..16 UTF-8 strings, total ≤4096 bytes, whose first element is an **absolute executable path**; no shell command string, PATH search, `-c`, inline code or `-m` expansion. Script arguments may be absolute file paths and literal flags; reject NUL/newline and arguments over 1024 bytes. The trusted user can intentionally authorize a host script, but song data cannot alter argv. Config must be a regular file, max 64 KiB, and parses with no duplicate keys; resolve plugin `path` and executable via `realpath`, require an absolute existing regular file or allowed plugin bundle directory, and reject symlink escape from the configured plugin root if one is set. Plugin root defaults to the parent of the configured path; do not derive it from the song. An absent config reads as `{version:1,plugins:{}}` for ordinary `doctor`, but a requested unknown ID, missing executable, or no command is `E_CAPABILITY` exit 3. For `doctor --plugins` and opted-in render/export, unreadable or malformed existing config is `E_ACCESS`/`E_INPUT` exit 4/2, respectively; ordinary `doctor` reports the code in `data.plugins.error` and stays successful; unreadable plugin path is `E_ACCESS` exit 4. Host commands and plugin paths are never copied to song, ProjectIR, public warnings or manifests.

[I] `music2 doctor --plugins [--plugin-host '<JSON argv>'] --json` actively sends one `probe` request per distinct selected argv and reports availability per configured ID. `doctor` without `--plugins` reports configured status (or `{configured:null,probed:false,error}` for an invalid/unreadable config) without spawning or failing, so the existing ffmpeg check remains safe. A selected pedalboard host is available only on exit 0, a single valid `ok:true` response, matching protocol and a `pedalboard` version ≥0.7.6 (R4 §5.1 reports instrument support at 0.7.4 and the initialization-timeout argument at 0.7.6, V); metadata-rich scan may recommend ≥0.9.4. A custom non-pedalboard host may report a distinct `hostVersion` and capability `audioEffect:true`; it need not pretend to be pedalboard. Detection is per invocation; no auto-install, scan of plugin directories or eager loading from a song. A requested ID is still checked at render time; a prior doctor result cannot authorize it.

## 3. JSON + WAV wire contract and resource limits

[I] D9/D14 select R4 §6's standard JSON+WAV process boundary over F24's provisional `request.json` plus 24-bit temp audio. Version is the exact string `music2-plugin-bridge/1`; a process receives **one** UTF-8 JSON object on stdin and emits **one** UTF-8 JSON object on stdout. Logs go to stderr. `render` uses an `input.kind:"wav"` path; the protocol reserves `input.kind:"midi"` event tuples for a later instrument bridge, but wp9 rejects MIDI input as unsupported. Each stage is a separate child so crash/timeout isolation covers each plugin. The known in/out paths are generated inside the private temp directory and passed as JSON data, never shell-interpolated.

```ts
export const PLUGIN_PROTOCOL = "music2-plugin-bridge/1" as const;
export type PluginRequest =
  | { protocol: typeof PLUGIN_PROTOCOL; op: "probe" | "selftest" }
  | { protocol: typeof PLUGIN_PROTOCOL; op: "render"; sampleRate: 44100 | 48000;
      channels: 2; bufferSize: 512; durationSec: number; tailSec: 0;
      input: { kind: "wav"; wavPath: string };
      chain: [{ path: string; pluginName: string | null;
        params: Readonly<Record<string, PluginValue>>; initTimeoutSec: 10 }];
      output: { wavPath: string; format: "f32" }; seed: number };
export type PluginResponse =
  | { protocol: typeof PLUGIN_PROTOCOL; ok: true; op: "probe";
      hostVersion: string; capabilities: { audioEffect: true }; pedalboard?: string }
  | { protocol: typeof PLUGIN_PROTOCOL; ok: true; op: "selftest";
      hostVersion: string; frames: 48000; sampleRate: 48000;
      peak: number; correlation: number }
  | { protocol: typeof PLUGIN_PROTOCOL; ok: true; wavPath: string; frames: number;
      sampleRate: 44100 | 48000; channels: 2; peak: number; rms: number;
      latencySamples: [number]; hostVersion: string; warnings: string[] }
  | { protocol: typeof PLUGIN_PROTOCOL; ok: false;
      error: { code: string; message: string } };
```

[I] Request `seed=fnv1a32(song.seed,track.id,"plugin",stageIndex)` from `src/shared/prng.tool.ts:4-17`; it is a hint to capable hosts, not a determinism promise. `durationSec=frames/sampleRate`, `tailSec=0`, `frames=round((durationSec+tailSec)*sampleRate)` exactly, and the output must preserve `frames`, rate and two channels. Because `frames/Fs` was formed from an integer frame count, the round trip is exact for supported lengths. The stage may use its plugin's reported latency internally; the host must return already aligned audio with **zero** added/removed frames. If the plugin adds a tail, the host truncates to the allotted buffer; a later protocol version may negotiate more tail. `bufferSize=512` and `initTimeoutSec=10` are wp9 defaults (I). The host process has a 60 s default total timeout (configurable as above), which includes initialization; never wait indefinitely. The host gets a minimal inherited environment (`PATH` omitted when absolute executable is used; preserve only platform-critical variables and explicit language/runtime variables), private cwd and no shell. Process tree termination uses SIGTERM then SIGKILL after 500 ms on POSIX, and platform-equivalent forced termination on Windows; timeout is `E_TIMEOUT` exit 7.

[V, R4 §6.4 / S32] Float WAV is RIFF/WAVE, 32-bit IEEE float, little-endian, interleaved stereo, `fmt ` size 18/tag `0x0003`, `fact` size 4 and `data`, so the canonical header is **58 bytes**, not 44. `[I]` Writer uses `RIFF.size=50+dataBytes`, `dataBytes=frames*2*4`, `byteRate=Fs*8`, `blockAlign=8`, `fact.frames=frames`. Reader walks chunks, honors odd pad bytes, permits `fmt` sizes 16/18/40 and format tags PCM 1, float 3 or extensible `0xFFFE` with supported PCM/float GUID only, but host output for wp9 **must** resolve to stereo f32. Reject missing/duplicate fmt/fact/data, inconsistent fact/byte lengths, RF64, nonfinite samples or any sample with `|x|>64` as `E_RENDER` exit 5; accept finite samples with `1<|x|<=64` and emit `PLUGIN_HEADROOM_EXCEEDED` warning. The explicit safety bound is inclusive; finite f32 samples are not restricted to PCM's `[-1,1]` because pre-master mixing does not clamp them. A host may write an unknown bounded chunk; it cannot make a 44-byte-header assumption. Do not change the main PCM WAV writer; existing `readWav` already walks chunks (`src/audio-io/wav.tool.ts:45-80`) but does not enforce the bridge's fact/output-format checks.

[I] Before allocation/writing, require `0 <= frames <= min(floor((0xffffffff-50)/8), 67108864)` and `8*frames <= 512 MiB`; bound the JSON request to 64 KiB, stdout to 64 KiB, stderr capture to its last 2 KiB, total input+output temp WAVs to 1 GiB. Use a 0700 `mkdtemp` beneath the OS temp root with exact `in.wav`/`out.wav` basenames. Reject absolute response paths other than the expected `out.wav`, symlinks and non-regular output; compare resolved path and opened file identity within the directory before decode. Clean on success, error, timeout and abort. A host has local code execution by user choice; these guards prevent untrusted **song** content from choosing that code and constrain accidental or malicious protocol output. No network or filesystem sandbox is promised.

Host stdout is protocol data only. Exit 0 with `ok:false` is an error; exit nonzero with `ok:true` is also an error. The optional MIT Python bridge uses R4 §6's exit convention: 0 success, 2 invalid request, 3 plugin load failed, 4 render failed, 5 pedalboard missing. music2 maps missing library/host to `E_CAPABILITY` exit 3, malformed song/config flags to `E_INPUT`/`E_SCHEMA` exit 2, unreadable user paths to `E_ACCESS` exit 4, failed plugin/load/crash/wrong output to `E_RENDER` exit 5, timeout to `E_TIMEOUT` exit 7. Sanitized JSON errors identify the stage/ID and code, not host stderr or local paths. A diagnostic log may retain the bounded stderr tail locally with redaction; stdout remains a single music2 envelope (`src/cli/output.ts:4-33`, V).

## 4. Render injection, determinism and export behavior

```ts
export interface ExternalProcessor {
  process(trackId: string, plugins: readonly PluginUse[], audio: StereoBuffer,
    context: { bpm: number; seed: number; startSeconds: number }): Promise<StereoBuffer>;
}
export interface RenderOptions { external?: ExternalProcessor /* prior fields retained */ }
export interface RenderResult { deterministic?: false /* omitted if no plugin ran */ }
```

[I] `renderSong` checks presence of any nonempty plugin chain before `mixTracks`; without an injected processor it raises `E_CAPABILITY`, even for a silent track, so there is no accidental bypass. The `render` CLI and each audio-producing `export` flow construct injection only after `--allow-plugins`, read config only for the requested IDs, and do not run the host when no chain exists. `export stems` always needs audio; `export als`/`export dawproject` need audio for `--content audio|both` but not `--content midi`. Without opt-in, a plugin-bearing song fails the audio export with `E_CAPABILITY` exit 3 and the `--allow-plugins`/host-configuration fix hint before any artifact is staged. `export midi` and `export ir` never construct a host; MIDI-only DAW exports warn that plugin sound is absent. `--plugin-host` without `--allow-plugins` is `E_INPUT` for every export. The mixer runs plugin stages serially on a stereo copy after music2 track inserts. It validates returned length, rate and every sample as finite with `|x|<=64` at each stage before continuing. The process result replaces only that track's pre-fader source. Track gain/pan/duck/sends and the usual master path run afterward; stems therefore include the plugin sound. For a tapestop track with `--bars`, process the whole pre-roll source before the existing crop (`src/render/mixer.tool.ts:283-308`); other plugins with internal state still make no byte-identity or crop-equality promise. If no chain is used, no buffer copy, host load, path lookup or changed float operation occurs.

[I] The returned `RenderResult`/CLI JSON adds `deterministic:false` **only when at least one stage completed** and a `warnings` entry such as `external plugin audio may vary between renders`. A failed stage writes no final WAV. Plugin names/paths/host versions and temporary paths are absent from output metadata. Legacy `validate`, `events`, JSON, PCM and WAV stay pinned by wp2's D10 baseline, including the no-plugin `--allow-plugins` case. External plugin output, plugin-bearing stems and frozen DAW audio are excluded from byte hash claims, even if one host happens to repeat; export MIDI/ALS/DAWproject warning text must say plugin processing requires frozen audio to retain sound. Do not serialize an unhosted plugin as if DAW playback would match.

## 5. Optional Python host and license boundary

[V, R4 §5.1/S12/S26/S27] pedalboard supports VST3 across macOS/Windows/Linux and AU on macOS; its instrument support began in 0.7.4. Its package is GPLv3. [V, R4 §5.3/S31] The GNU GPL FAQ distinguishes ordinary pipes/files between processes from shared-address-space linking, while cautioning that very intimate interprocess data structures may still be treated as one program. [I] music2 core stays MIT and has zero runtime dependencies. `scripts/music2-plugin-bridge.py` carries its own MIT header, imports pedalboard only when executed as a user-selected separate program, accepts plain JSON and standard WAV bytes, and is never imported by TypeScript, packaged with pedalboard or run in CI. Distributing a separate environment that includes pedalboard requires the distributor to review and meet the GPLv3 terms for that environment; this is an engineering boundary, not a legal guarantee. No GPL/AGPL/LGPL source is read/copied for the implementation (D11/D14).

[I] The script validates the one-object request and exact paths, loads one effect by config-supplied path/name with `load_plugin(..., initialization_timeout=10)`, applies its numeric/string/boolean supported parameters through pedalboard's documented API, processes stereo float32 samples in declared order, writes canonical f32 WAV using Python stdlib `struct`, and prints one JSON result. Unsupported parameter names/types fail rather than being ignored. `probe` imports pedalboard and reports version/capability without loading a third-party plugin. `selftest` uses built-in `Gain(gain_db=-6)` and the Boundary vector 8 oracle. It has no install subcommand, download path or implicit plugin search.
