# 050 — Automation lanes (wp6)

**Summary.** Add arrangement-absolute automation lanes for gain, pan, sends, a deliberately small insert subset, and selected voice parameters. Song v1 resolves beats to PPQ-960 ticks; the renderer evaluates linear/hold lanes at each audio frame, smooths abrupt control changes, and samples voice controls once at note onset. The old mixer path remains byte-identical when `automation` is absent. **I** = music2 design choice; **V** = verified external-format fact. ## 1. Wire shape, ownership and validation

I: Song v1 examples (both `tracks[]` and `audioTracks[]` accept the same `automation` key):

```json
{"automation":[
  {"target":"gain","points":[{"at":0,"value":-12},{"at":16,"value":0}]},
  {"target":"pan","points":[{"at":0,"value":-1},{"at":4,"value":1,"curve":"hold"}]},
  {"target":"send.reverb","points":[{"at":0,"value":0},{"at":8,"value":0.6}]},
  {"target":"fx.0.cutoffHz","points":[{"at":0,"value":400},{"at":8,"value":4000}]},
  {"target":"param.cutoffHz","points":[{"at":0,"value":300},{"at":8,"value":2400}]}
]}
```

I (F7, D6): wp2 `song-daw.schema.ts` owns all structural validation below; wp6 reads those resolved lanes. `target` matches `^(gain|pan|send\.(reverb|delay)|fx\.(0|[1-9][0-9]?)\.[A-Za-z][A-Za-z0-9]*|param\.[A-Za-z][A-Za-z0-9]*)$`. Use `automation?: AutomationLaneInput[]`, at most 32 lanes per track, one lane per target; `points` 1..4096; each point `{at:number,value:number,curve?:"linear"|"hold"}` with default `linear`. `at` is finite ≥0 beats from song start, non-decreasing, ≤ arrangement body beats. At most two points share a beat; if two, the first is the pre-step value and the second is the new value, effective at that beat. A third is invalid. Last point's `curve` is accepted but has no outgoing segment. `value` finite; `gain` −60..12 dB, `pan` −1..1, sends 0..1. These are music2 ranges, not MIDI's native units (`src/song/song.schema.ts:78-85`; `evidence/architect-proposal.md:238-266`).

I: `fx.i.p` requires an existing track insert at zero-based index `i`, a numeric `INSERT_SPECS` property and the whitelist below; never master inserts. Values use that parameter's inclusive range/default from `src/render/fx/fx.schema.ts:21-34`. `param.p` requires a built-in voice whose `VoiceSpec.automatable` contains `p`, then the voice's numeric `ParamSpec` bounds/integer rule (`src/render/voices/registry.tool.ts:66-98`). `kit:`, `sfz:`, audio tracks and non-opted-in voices reject `param.*`; audio tracks may use mixer and insert targets. A missing `send.reverb`/`send.delay` static field is valid and defaults to 0 (`src/song/song.schema.ts:361-364`). Lanes replace the static field for the entire song; before first point use first value, after last use last. The static field applies only when its lane is absent (F7).

I: wp2 alone validates and stores resolved points as `{tick:number,value:number,curve:"linear"|"hold"}`; `tick=beatsToTicks(at)` using PPQ 960, safe nonnegative half-up rounding (F1). Reject a pair of distinct input beats that quantize to the same tick **unless** their original `at` values are equal (an intentional step); issue at the later `.at`. This prevents accidental zero-length segments. Preserve input order for two equal-time points. `ResolvedTrack.automation` and `ResolvedAudioTrack.automation` are omitted when input omitted, not `[]` (D1/F9). `ProjectIR` copies these resolved tick lanes (F3), while render never imports ProjectIR (D1/F2/F13).

I: wp2 structural/cross-field failures are `E_SCHEMA` exit 2 with `details.issues:[{path,message}]`; representative exact paths: `$.tracks[0].automation[1].target` for malformed/duplicate/unsupported target; `$.tracks[0].automation[1].points[2].at` for unordered/colliding/out-of-body time; `$.tracks[0].automation[1].points[2].value` for nonfinite/range; `$.audioTracks[0].automation[0].target` for a disallowed voice lane. Voice-specific failures may be raised at render validation with `tracks[0].automation[1].target`/`.points[2].value`, matching the existing non-`$` voice-issue style (`src/render/voices/registry.tool.ts:81-97`); prefer wp2 song validation to emit the `$` path when it can know the voice. Invalid `fx.3.cutoffHz` on a two-insert track reports the target path, never clamps or silently ignores it. No new error code (F16).

## 2. Curve math and DSP smoothing

I: The automation-only module API is:

```ts
import type { ResolvedLane } from "../song/song-daw.schema.ts"; // sole resolved type owner is wp2
// parseTarget, AutomationTarget and resolveLanes are declared only in song-daw.schema.ts.
export function valueAt(lane: ResolvedLane, tick: number): number;
export function renderCurve(lane: ResolvedLane, opts: {
  frames: number; sampleRate: number; bpm: number; startTick: number;
}): Float32Array;
export function smoothCurve(raw: Float32Array, opts: {
  sampleRate: number; initialValue: number;
}): Float32Array;
```

I: For distinct ticks `t0<t1`, `u=(tick−t0)/(t1−t0)` and outgoing shape belongs to the **left** point: linear `a+(b−a)u`, hold `a` for `t<t1`. At exactly `t1`, use the right point. For two points at the same tick `T`, left limit comes from the first, but `valueAt(T)` returns the **second**. `valueAt` uses upper-bound search for the last point at or before `tick`; before first return first value; after last return last. No `power` or tension field in Song v1 (D6 overrides R1's optional three-shape suggestion; V DAWproject supports only hold/linear: `evidence/aside-notes/R1_midi_automation_stems.md §4.3, §4.5`).

I: Audio frame `i` is evaluated at `tick = startTick + i*(bpm*960)/(60*sampleRate)` in float64; `startTick` is the absolute bar-origin tick for a partial render and 0 for pre-roll. Store the result once into `Float32Array[i]`. Do not round every audio frame to an integer tick; that would make 960 discrete steps per beat. Pattern events retain their original float seconds and frames; for `param.*` onset sampling only, project onset to ticks with `secondsToTicks(event.time,bpm)`, without moving the note (F2/F4). List-note onset ticks are already exact (F5/F10). Body-end value holds through the render tail.

I: `renderCurve` is the raw mathematical lane for export-equivalent evaluation. Before audio use, apply one causal 5 ms one-pole control smoother to **each** used lane: `alpha=1−exp(−1/(0.005*Fs))`, `y[0]=initialValue`, `y[i]=y[i−1]+alpha*(raw[i]−y[i−1])` for subsequent frames; when pre-roll begins at song frame 0, `initialValue=raw[0]`. Smoothing affects DSP only, not Song/ProjectIR/MIDI/XML values. This makes a hold or duplicate-time step approach its new value without a one-frame zipper jump. All automated partial tracks, including a tapestop track, run their own voice/clip + insert + smoother from absolute frame 0 through requested end and are cropped **after** insert processing; that preserves smoother/filter/delay state and matches full render for the same track window. Compute the duck envelope and bus sends for the requested window, using the same absolute event address; do not double-process track audio. No-lane `--bars` remains on the current path (`src/render/mixer.tool.ts:263-310`).

I: Guard `frames` as safe nonnegative integer, `Fs∈{44100,48000}` and `bpm` in song range 40..240 at the render boundary; validate each generated value finite, with `E_RENDER` and `{track,target,frame}` for any nonfinite curve/audio. No per-point/per-frame object allocation. A track's memory is O(frames × active lanes), reusing or releasing arrays after its mix; upper bound 32 lanes is a safety limit, not a target workload.

## 3. Mixer, inserts and voices

I: `AUTOMATABLE_INSERT_PARAMS` is the single wp2 validation constant in `src/render/fx/fx.schema.ts`, defined exactly in `010_project_ir.md` §2: filter `cutoffHz`; EQ `lowGainDb`, `midGainDb`, `highGainDb`; drive `amount`; tremolo `depth`; delay `mix`; width `amount`. wp6 renders exactly those parameters; compressor, chorus, phaser, crush and tapestop have no automatable parameters in this phase. Do not redefine or widen the list in the DSP path.

I: Ranges/defaults are **inherited, not duplicated**: `filter.cutoffHz` 20..18000 Hz/1000; EQ `*GainDb` −18..18 dB/0; `drive.amount` 1..12/2; `tremolo.depth` 0..1/0.5; `delay.mix` 0..1/0.35; `width.amount` 0..2/1 (`src/render/fx/fx.schema.ts:21-33`). `FxContext.curves` keys are parameter names for the **current** insert only; `applyInsertChain` chooses lanes matching its integer effect index. Every dynamic branch checks `curves?.[p]` once outside sample loops. An insert without curves executes its current static branch bit for bit (`src/render/fx/index.ts:25-38`).

I: Filter automated cutoff uses 32-frame held coefficients at smoothed value of the block's first frame; if LFO is enabled, preserve the current left-sine/right-cosine SVF phase at the absolute frame (`src/render/fx/filter.tool.ts:20-33`). EQ uses 32-frame coefficient blocks for each band with persistent L/R biquad state; process even zero-dB bands in the automated branch to prevent a discontinuous topology switch (`src/render/fx/eq.tool.ts:4-11`; `src/render/fx/biquad.tool.ts:49-63`). Drive `amount`, tremolo `depth`, delay `mix` and width `amount` read smoothed values **per sample**; drive's normalization is `tanh(amount)` per sample, delay's wet feedback is generated at unity and scaled only at the output, so changing mix cannot change echo feedback (`src/render/fx/drive.tool.ts:16-39`; `src/render/fx/tempo-delay.tool.ts:7-50`). 32-frame filter/EQ control quantization is an I CPU tradeoff; smoother limits the maximum 32-frame jump. In an automated branch with a constant curve equal to the static value, output must match the static processor within `1e-6` float per sample; any state/phase discontinuity is a defect.

I: `mixAutomated` takes the already processed mono or stereo buffer, per-frame smoothed controls, optional duck and optional stem. For each frame, `g=10^(gainDb/20)`, `L=g*cos((pan+1)π/4)*√2`, `R=g*sin((pan+1)π/4)*√2`; multiply by duck, sum L/R into master, then into reverb/delay send buffers using that frame's send values, and write the dry post-fader stem. This matches the current equal-power and accumulation law (`src/render/mixer.tool.ts:64-99`); master/return order is unchanged (`:338-361`). At `pan=0`, both factors equal `g`; at `pan=-1`, left factor is `g√2`, right is 0. Audio-track stereo buffers use the same channel-local factors. A gain lane of −60 dB is `0.001`, not digital silence. wp6 owns one bus-presence predicate for both instrument and audio tracks: positive static send OR a send lane with `max(points[].value)>0`. Use it at `src/render/mixer.tool.ts:338-346` and for wp4 return-null capture; test zero static send rising by automation.

I: First voice set is `bass.cutoffHz` 40..8000 Hz/600, `pad.cutoffHz` 80..12000 Hz/1800, `lead.vibratoCents` 0..100 cents/12 (`src/render/voices/bass.tool.ts:84-99`; `src/render/voices/pad.tool.ts:6-23`; `src/render/voices/lead.tool.ts:6-19`). `VoiceSpec.automatable` lists only those fields. In `selectEvents`, when a `param.*` lane exists, set `event.params={p: valueAt(lane,onsetTick)}` for each event; use the **raw**, unsmoothed lane at its onset and hold for that note's full lifetime, including release. Every opted-in voice reads `event.params?.[p] ?? params[p]` once per event. The bass mono legacy branch currently captures alpha before its event loop (`src/render/voices/bass.tool.ts:15-25`); move alpha calculation inside the event loop **only on the automation branch**, keeping no-lane floats unchanged. For a same-frame retrigger, follow current skip/mono stop behavior (`src/render/voices/bass.tool.ts:25-31`). Reject `param.cutoffHz` on a `kit:` or `sfz:` track rather than implying sampler opcode support.

## 4. MIDI CC and downstream envelope handoff

V: MIDI CC7 is Channel Volume and CC10 is Pan; CC10 center is 64, hard right 127, hard left 0. CC91 is Effects 1 (reverb send), and CC74 is named Brightness rather than a specified cutoff-in-Hz mapping (`evidence/aside-notes/R1_midi_automation_stems.md §3, §3.2`; [MIDI CC table](https://midi.org/midi-1-0-control-change-messages)). I: D6/F17 bind the first MIDI set to **CC7 and CC10 only**; `send.*`, `fx.*`, `param.*` are omitted from MIDI with one warning per affected target, preserving the native lane in ProjectIR for wp7/wp8. Do not silently map reverb send to CC91 or Hz to CC74 without a separate contract.

I (F17 wins over R1 §4.5's generic grid suggestion):

```ts
export function gainDbToCc7(db: number): number; // clamp(round(127*10**(db/40)),0,127)
export function cc7ToGainDb(cc: number): number; // cc=0 -> -60; else clamp(40*log10(cc/127),-60,12)
export function panToCc10(pan: number): number;  // clamp(round(64+63*pan),0,127)
export function cc10ToPan(cc: number): number;  // clamp((cc-64)/63,-1,1)
export interface CcEvent { tick: number; controller: 7 | 10; value: number }
export function laneToCcEvents(lane: ResolvedLane, endTick: number): CcEvent[];
export function ccEventsToLane(target: "gain" | "pan", events: readonly CcEvent[]):
  { staticValue: number; lane?: never } | { staticValue?: never; lane: ResolvedLane };
```

I: CC value inputs are integers 0..127; helpers reject invalid numbers with `E_INPUT`, not clamp them. Gain/pan inputs are finite within Song bounds; converter clamps **output** only. At −60 dB CC7=4, −12 dB=64, −6 dB=90, 0 dB=127, +12 dB=127. At pan −1/0/+1 CC10=1/64/127. Import applies `cc7===0 ? -60 : max(-60,min(12,40*log10(cc7/127)))` and `max(-1,min(1,(cc10-64)/63))` exactly: CC7 0..3 land on the Song −60 dB floor and re-export as 4; CC10 0 lands on −1 and re-exports as 1. These are lossy inputs; emit `MIDI_CC_CLAMPED:<trackId>.<controller>@<tick>=<value>` once for each affected retained CC event, including a sole tick-0 static value (wp3), with controller `7` or `10`. For CC7 4..127 and CC10 1..127, the import→export oracle compares integer CC values at retained message ticks exactly; CC7 0..3→4 and CC10 0→1 are the explicit exceptions. CC7's positive-gain region collapses to 127, so a Song→MIDI→Song round-trip cannot recover +dB gain; emit `gainCcClipped:<trackId>` warning whenever a gain field/lane contains `>0`. These are product quantization laws, **not** a claim of any DAW's mixer mapping (V limits: `evidence/aside-notes/R1_midi_automation_stems.md §3.2`).

I: Writer emits static or lane-effective CC7/CC10 at tick 0, then samples linear segments at multiples of 120 ticks and each exact lane point tick, sorting by tick then controller; hold emits only its new endpoint. Emit only changed 7-bit values, except the first tick-0 value. For duplicate-time points, emit the right/effective value at that tick, never two same-controller messages at the same tick. The grid is F17's 120 ticks (an eighth beat); raw lane points guarantee exact endpoints. Per wp3's shared-channel contract (`020_midi.md` §3), only the first channel-10 drum-kind track may emit CC7/10; later such tracks omit independent gain/pan automation and warn `DRUM_MIX_LOSS` plus `MIDI_AUTOMATION_OMITTED:<trackId>.<target>`. A reused pitched channel likewise warns that CCs may affect another instrument. Reader groups per channel/controller, applies last-value-wins at a shared tick, and creates one point per retained CC message with outgoing `curve:"hold"`; a sole tick-0 CC returns `staticValue` for `gain`/`pan`, while multiple changes return `lane` with the first tick-0 value (or first value before its first tick per F7). Round-trip comparison is exact 7-bit CC values at retained message ticks for CC7 4..127 and CC10 1..127, with the clamp exceptions above; compare neither original dB nor linear shape. `ccEventsToLane` is independent of SMF parsing; wp6 wires it into wp3's running-status-capable reader (V: `evidence/aside-notes/R1_midi_automation_stems.md §1.6, §3`).

## Boundary vectors

These are contract oracles for implementation, not measured results.

1. `[{tick:0,value:0,linear},{tick:960,value:1}]`: `valueAt(0)=0`, `valueAt(240)=0.25`, `valueAt(480)=0.5`, `valueAt(960)=1`, `valueAt(1200)=1`.
2. Same endpoints with outgoing `hold`: values at 0/480/959 are 0; at 960 and later are 1.
3. `[{0,0,linear},{960,1,linear},{960,0.2,hold},{1920,0.5}]`: `valueAt(959)=959/960`, `valueAt(960)=0.2`, `valueAt(1919)=0.2`, `valueAt(1920)=0.5`.
4. One point `{at:4,value:-6}` gives −6 before, at and after beat 4; it replaces the static track gain throughout.
5. 120 BPM, 48 kHz: beat 1/tick 960 occurs at frame 24000; raw linear 0→1 over one beat gives frame 12000 = 0.5.
6. At 1 kHz synthetic smoother test rate and 5 ms constant, an upward hold step at frame 500 has `alpha=1−exp(−0.2)=0.181269247`; output frame 500 is that value and frame 505 is `1−exp(−1.2)=0.698805788` (±1e−6). The production rate whitelist still applies at render boundary.
7. Two points at beat 1 are legal; three at beat 1 reject `E_SCHEMA` at `$.tracks[0].automation[0].points[2].at`. Points at 1 and 0.5 reject the second `.at`.
8. At PPQ 960, `at=1/3840` and `at=0` are distinct but both round to tick 0, so reject the later `.at`; two literal `at=0` points are the intentional step.
9. A 4/4 bar at 120 BPM is 2 s. A partial render from bar 2 of an automated filter/hold-step track equals the matching full-render PCM window, including its 5 ms smoother state and insert tail, on the same Node/platform.
10. `fx.0.cutoffHz` with filter at insert 0 accepts 400→4000 Hz; with EQ at insert 0 it rejects the target. `fx.2.cutoffHz` on a two-insert track rejects the target.
11. Filter cutoff 19/18001 Hz and EQ gain −18.001/18.001 dB fail value bounds; 20/18000 Hz and −18/18 dB pass. Integer-only voice params remain integer-only even if later whitelisted.
12. `param.cutoffHz` on bass at event ticks 0 and 960 with points 300→2400 yields onset overrides 300 and 2400; first note holds 300 through release even after the lane changes. A `kit:` track rejects this target.
13. Bass/pad/lead without a `param.*` lane render exact old PCM; a constant lane equal to static value renders equal within `1e−6` (voice event allocation may differ, sample values must not).
14. Center pan 0 gives L=R for mono; hard-left pan −1 gives R=0 and L=`√2×gain×sample`, before duck. A −6 dB lane gives `10^(−6/20)=0.5011872336` linear gain at its exact endpoint.
15. Static `send.reverb=0` plus lane 0→0.5 produces a nonzero reverb send buffer/return after the change; dry stem excludes the return. Sum(track stems + returns) equals premaster within float tolerance set by wp4.
16. `gainDbToCc7(-60,-12,-6,0,12)` yields `[4,64,90,127,127]`; `cc7ToGainDb(0)=-60`, `cc7ToGainDb(127)=0`, `cc7ToGainDb(64)≈−11.90495` dB (±0.00001).
17. `panToCc10(-1,0,1)` yields `[1,64,127]`; `cc10ToPan(0)=-1`, `(64)=0`, `(127)=1`.
18. A hold `gain` step at tick 960 writes CC7 at tick 0 and 960 only. A linear ramp −12→0 over 960 ticks samples 0,120,…,960 plus exact point ticks, suppressing any duplicate CC value.
19. Two lane points at tick 960 with old/new values yield only the new CC at 960. Reader CC7 64 at tick 0 and 127 at tick 960 creates a hold lane; exporting it reproduces those two messages and never invents a linear ramp.
20. `send.delay`, `fx.0.cutoffHz`, and `param.cutoffHz` are absent from a MIDI track's CC stream and each yields a named omission warning; raw lanes remain in ProjectIR for wp7/wp8.
21. Imported CC7 `0,1,2,3` at tick 0 each decode to −60 dB, warn `MIDI_CC_CLAMPED:<trackId>.7@0=<value>`, and re-export as 4; imported CC7 `4,64,127` re-export as `4,64,127` without that warning. The same rule applies to a later retained CC7 event at tick 960 under wp6.
22. Imported CC10 `0` at tick 0 decodes to −1, warns `MIDI_CC_CLAMPED:<trackId>.10@0=0`, and re-exports as 1; imported `1,64,127` re-export as `1,64,127` without that warning. The same rule applies to a later retained CC10 event at tick 960 under wp6.
23. A track with `gain` and `pan` lanes exports their CC7/CC10 curves in wp6 and loses only those two wp3 `MIDI_AUTOMATION_OMITTED` warnings; its `send.delay` lane retains one. A second channel-10 drum-kind track exports neither lane and retains one warning per lane plus `DRUM_MIX_LOSS`.
21. Two channel-10 drum-kind tracks with different gain lanes emit CC7 for the first only; the second emits no CC7 and reports `DRUM_MIX_LOSS` plus its named automation-omission warning (`020_midi.md:128-134`).
22. Legacy songs with no `automation` keep identical PCM/WAV, `validate --json`, `events --json`, lint and stem bytes to the D10 pre-unit receipt on its pinned platform; no added empty arrays, no extra event property.
